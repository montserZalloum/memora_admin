# Challenge Hub Full Flow (ASCII)

This document describes the current implementation in code for Challenge Hub, not only the intended PRD flow.

Important current-code notes:

- `GET /api/v1/challenge/hierarchy` returns a field named `stamped_topics`, but the service currently counts topics that are either `stamped` or already `open`.
- Empty topics (`mcq_count == 0`) are hidden from the response and only auto-stamp virtually inside the unlock-chain computation. No explicit progress row is written for an empty topic.
- The generated challenge question file path is currently `challenges/{topic_id}.json`.
- The current builders/query helpers do not filter `Memora Review Item.stage_type = "QUESTION"` when counting/exporting challenge questions. They read all Review Item rows for the topic as the code stands today.

## 2. Content Hierarchy Used by Challenge Hub

```text
Memora Subject
`-- Memora Track
    `-- Memora Unit
        `-- Memora Topic
            |-- visible challenge node
            |-- has computed mcq_count
            `-- Memora Lesson
                `-- Memora Lesson Stage
                    `-- sync_review_items()
                        `-- tabMemora Review Item
                            |-- QUESTION
                            |-- FILL_BLANK
                            |-- MATCHING
                            |-- MINDMAP
                            `-- generic extracted item types
```

What Challenge Hub actually uses from that tree:

- Subject list comes from the player plan manifest.
- Track/unit/topic structure comes from `get_subject_hierarchy()`.
- `mcq_count` comes from `get_question_counts_by_topic(subject_id)`.
- Question payloads for a topic come from `Memora Review Item` rows for that topic.
- Unlock condition `normal_path_complete` comes from the normal progress stats cache, not from challenge progress.

## 4. Exact Browse Flow

### 4.1 Subject Landing Cards

```text
Player opens Challenge Hub landing page
`-- GET /api/v1/challenge/hierarchy
    |
    +-- fastapi_app/api/v1/endpoints/challenge.py
    |   `-- get_challenge_hierarchy_list()
    |
    `-- ChallengeService.get_challenge_subjects()
        |
        +-- PlanService.get_manifest(plan_id)
        |   `-- memora_admin.api.plan.get_plan_manifest()
        |       |-- read plans/{plan_id}/manifest.json from storage if present
        |       `-- else generate plan JSON on the fly
        |
        +-- HierarchyService.get_hierarchy(subject_id) for each subject
        |   `-- memora_admin.api.hierarchy.get_subject_hierarchy()
        |
        +-- bulk hydrate challenge progress Redis hashes on cache miss
        |   `-- memora_admin.api.challenge.get_player_challenge_progress_bulk()
        |
        +-- bulk read per-subject challenge progress maps from Redis
        +-- bulk read/recompute normal-path stats
        +-- bulk resolve subject access
        +-- read leaderboard XP by subject when season+plan exist
        |
        `-- compute summary card values per subject
            |-- total_topics
            |-- stamped_topics
            `-- total_challenge_xp
```

Summary card computation details:

- `total_topics` ignores empty topics (`mcq_count == 0`).
- `stamped_topics` currently counts topics that are:
  - explicitly stamped, or
  - currently open.
- `total_challenge_xp` comes from subject leaderboard ZSET when available, else from summing stored topic progress.

### 4.2 Subject Detail Tree

```text
Player opens one subject in Challenge Hub
`-- GET /api/v1/challenge/hierarchy/{subject_id}
    |
    +-- fastapi_app/api/v1/endpoints/challenge.py
    |   `-- get_challenge_hierarchy_detail()
    |
    `-- ChallengeService.get_challenge_hierarchy()
        |
        +-- verify subject_id exists in player's plan manifest
        +-- load hierarchy tree for subject
        +-- load player challenge progress map
        +-- load valid normal-path stats
        +-- resolve subject access
        +-- build free_units / free_topics sets from hierarchy
        |
        `-- walk tracks -> units -> topics
            |
            +-- for each unit:
            |   `-- prev_stamped = True
            |
            +-- for each topic:
            |   |
            |   +-- if mcq_count == 0
            |   |   |-- hidden from response
            |   |   `-- if prev_stamped is True, auto-stamp chain continues
            |   |
            |   +-- else read explicit player topic progress
            |   +-- compute has_access
            |   +-- compute normal_path_complete
            |   +-- predecessor_stamped = prev_stamped
            |   |
            |   +-- state = stamped
            |   |   `-- if explicit progress says stamped
            |   |
            |   +-- state = open
            |   |   `-- if has_access && normal_path_complete && predecessor_stamped
            |   |
            |   `-- state = locked
            |       `-- first failing reason wins:
            |           |-- NO_ACCESS
            |           |-- NORMAL_PATH_INCOMPLETE
            |           `-- PREVIOUS_NOT_STAMPED
            |
            `-- after each non-empty topic:
                `-- prev_stamped = explicit stamped only
```

Important implications of the current unlock code:

- Sequence resets at the start of every unit because each unit starts with `prev_stamped = True`.
- A topic that is merely `open` does not unlock the next topic. It must become explicitly `stamped`.
- Empty topics do not appear in the API response.
- Empty topics also do not create stored progress entries; the auto-stamp behavior is computed on the fly.
- If a player has no paid subject access but the subject contains any free unit/topic, the detail endpoint still returns tracks and units, and each topic decides its own `has_access`.

## 5. Unlock Logic as an ASCII Decision Tree

```text
For one non-empty topic
|
+-- 1) Is topic explicitly stamped in challenge progress?
|   |
|   +-- Yes -> state = stamped
|   `-- No
|
+-- 2) Does player have access?
|   |
|   +-- No -> state = locked, lock_reason = NO_ACCESS
|   `-- Yes
|
+-- 3) Is normal path complete for this topic?
|   |
|   +-- No -> state = locked, lock_reason = NORMAL_PATH_INCOMPLETE
|   `-- Yes
|
`-- 4) Is predecessor stamped?
    |
    +-- No -> state = locked, lock_reason = PREVIOUS_NOT_STAMPED
    `-- Yes -> state = open
```

Empty-topic chain behavior:

```text
Visible topic A -> Empty topic B -> Empty topic C -> Visible topic D

If A is not stamped:
  B stays virtually locked
  C stays virtually locked
  D stays locked

If A becomes stamped:
  B becomes virtually stamped
  C becomes virtually stamped
  D can become open if access + normal completion are also true
```

## 6. Exact Play / Submit / Persist Flow

```text
Player starts a topic challenge
|
+-- frontend loads generated topic file from CDN
|   `-- challenges/{topic_id}.json
|
+-- frontend randomizes question order locally
|
+-- player answers every question in one sitting
|
`-- frontend submits one batch
    `-- POST /api/v1/challenge/attempt
        |
        +-- FastAPI endpoint claims idempotency key
        |   `-- memora:ch:idem:{player_id}:{attempt_key}
        |
        `-- ChallengeService.submit_attempt()
            |
            +-- load challenge settings
            +-- load per-topic question lookup
            +-- server-grade answers using chosen_answer vs correct_choice
            +-- acquire per-player+subject+topic Redis lock
            +-- hydrate + load existing topic progress
            +-- validate topic is open unless it was already stamped
            +-- update best scores
            +-- compute XP delta
            +-- compute stamped / attempt_number / total_topic_xp
            +-- build progress JSON
            +-- build attempt-buffer JSON
            |
            `-- one Redis pipeline writes:
                |-- HSET memora:ch:progress:{player}:{subject}
                |-- EXPIRE progress hash
                |-- SADD memora:dirty:ch_progress
                |-- RPUSH memora:ch:attempt_buffer
                |-- RPUSH memora:buffer:interactions (FSRS entries)
                |-- ZINCRBY plan leaderboard if xp_delta > 0
                `-- ZINCRBY subject leaderboard if xp_delta > 0
```

### 6.1 What the Server Trusts vs Ignores

```text
Client sends for each question:
  item_id
  correct
  time_spent
  chosen_answer

Server behavior:
  chosen_answer -> trusted for grading
  correct       -> ignored when canonical correct_choice lookup exists
  total_questions -> required by schema, but grading uses len(questions)
                     and question_lookup size, not this field directly
```

If the server can load `question_lookup`, it does all grading server-side.

If the lookup cannot be loaded at all, the service falls back to trusting the client `correct` flags, but that is degraded behavior.

### 6.2 Duplicate / Retry Protections

```text
Idempotency layer
`-- memora:ch:idem:{player}:{attempt_key}
    |-- first request sets "__pending__"
    |-- completed request stores full response JSON for 5 minutes
    `-- duplicate request gets HTTP 409

Mutation lock
`-- memora:ch:lock:attempt:{player}:{subject}:{topic}
    `-- prevents two concurrent submissions from double-awarding XP
```

### 6.3 Durable Flush Path

```text
Redis write completed
`-- memora_admin/tasks/sync.py :: sync_dirty_challenge_progress()
    |
    +-- every 1 minute
    |
    +-- Job 1: dirty challenge progress
    |   |
    |   +-- SPOP memora:dirty:ch_progress
    |   +-- read memora:ch:progress:{player}:{subject}
    |   `-- upsert tabMemora Challenge Progress
    |
    `-- Job 2: attempt buffer
        |
        +-- LRANGE memora:ch:attempt_buffer
        +-- insert tabMemora Challenge Attempt
        +-- insert child rows into tabMemora Challenge Attempt Detail
        +-- LTRIM processed batch
        `-- re-queue failures
```

The system is intentionally split into:

- fast path: Redis writes inside the API request,
- slow path: periodic MariaDB flush for durable analytics/audit storage.

## 7. Leaderboard Flow

```text
XP earned on attempt
`-- if xp_delta > 0
    |
    +-- memora:lb:ch:{season_id}:plan:{plan_id}
    |   `-- total challenge XP across all subjects in the plan
    |
    `-- memora:lb:ch:{season_id}:plan:{plan_id}:subject:{subject_id}
        `-- subject-scoped challenge XP
```

Read path:

```text
GET /api/v1/challenge/leaderboard
`-- read page window from ZSET
    `-- dense-rank calculation
        `-- batch profile lookup

GET /api/v1/challenge/leaderboard/me
`-- read player's ZSET position + score
    `-- compute dense rank + neighbors + xp_to_next
```

Challenge leaderboard isolation:

- No writes go to the main wallet keys.
- No writes go to the main leaderboard keys.
- Challenge XP lives only in challenge progress hashes and challenge leaderboard ZSETs.
