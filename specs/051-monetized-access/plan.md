# Implementation Plan: Monetized Access

**Branch**: `051-monetized-access` | **Date**: 2026-03-18 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/051-monetized-access/spec.md`

## Summary

Implement a monetized access system that introduces Plan Premium (unlocks all gated content within a Study Plan for the remainder of a Season) and Paid Live Events (ticket-gated events with premium bypass). Three entitlement sources: payment gateway purchase, promotional voucher redemption, and admin grant. Access validity is computed at runtime (no stored expiry) with two-layer concurrency control (Redis locks + MariaDB virtual column unique indexes). Financial records (Purchase, Invoice) are strictly separated from access entitlements (Premium, Event Access).

## Technical Context

**Language/Version**: Python 3.11 (Frappe v15)
**Primary Dependencies**: Frappe v15, FastAPI, Redis, MariaDB, ERPNext (Sales Invoice)
**Storage**: MariaDB (source of truth) + Redis (hot cache with self-healing hydration)
**Testing**: pytest + httpx (FastAPI), FrappeTestCase (Frappe), concurrent threading tests
**Target Platform**: Linux server (Ubuntu 22.04)
**Project Type**: Web — dual architecture (Frappe admin panel + FastAPI game API sidecar)
**Performance Goals**: <10ms premium usability check, <50ms p95 access resolution, <60s purchase flow (excluding gateway)
**Constraints**: JOD currency (3 decimal places), sub-20ms game API (Constitution Principle II), HMAC-SHA256 voucher codes (Principle V), Frappe ORM for invoices (Principle VI)
**Scale/Scope**: 6 new DocTypes, 1 extended DocType, 2 new FastAPI services, 2 new Frappe API modules, 2 new event sync modules, ~15 new endpoints

## Key Design Decisions

| Decision | Reference | Rationale |
|---|---|---|
| Virtual column unique indexes instead of partial unique indexes | R-001 | MariaDB doesn't support WHERE in UNIQUE INDEX |
| Rename to "Access Voucher" (not "Voucher Card") | R-002 | Avoid collision with existing B2B Memora Voucher Card DocType |
| Single webhook endpoint with purchase_type routing | R-003 | Reuses existing webhook pattern, avoids endpoint duplication |
| 3-tier cached premium check (local → Redis → DB) | R-004 | Meets <10ms target while following self-healing cache principle |
| Premium bypass as Gate 1.5 in access flow | R-005 | Additive extension, no changes to existing Gate 2 logic |
| Redis SET NX EX locks + DB virtual column safety net | R-006 | Follows existing plan_change.py pattern, defense-in-depth |
| Premium survives plan change (computed validity) | R-007 | FR-013: status only modified by explicit business actions |
| HMAC-SHA256 for access voucher codes | R-009 | Constitution Principle V (NON-NEGOTIABLE) |
