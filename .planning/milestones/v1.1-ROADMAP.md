# Milestone v1.1: Feature Expansion

**Status:** SHIPPED 2026-02-03
**Phases:** 8-11
**Total Plans:** 13

## Overview

Extend the platform with game sessions for lesson flow tracking, competitive leaderboards, device management for security, and scheduled maintenance tasks.

## Phases

### Phase 8: Device Management

**Goal**: Secure device registration with 3-device limit enforcement
**Depends on**: Phase 2 (JWT authentication)
**Requirements**: DEVICE-01, DEVICE-02
**Plans**: 2 plans
**Completed**: 2026-02-03

**Success Criteria:**
1. User's device is registered with metadata on login
2. User with 3 devices is blocked from logging in on 4th device
3. Device registration is atomic (no race conditions with concurrent logins)

Plans:
- [x] 08-01-PLAN.md — Device service foundation (models, Lua script, DeviceService)
- [x] 08-02-PLAN.md — Login integration and admin removal hook

**Details:**
- Fingerprint uses stable UA components (no versions) for device recognition
- Lua script for atomic device registration with race condition prevention
- Device hash structure: memora:devices:{user_id} with device:{id}:{attr} fields
- HTTP 429 for device limit exceeded (matches rate limiting semantics)
- Immediate session invalidation on admin device removal

### Phase 9: Game Sessions

**Goal**: Lesson flow tracking with session lifecycle and validation
**Depends on**: Phase 4 (progress tracking), Phase 8 (device metadata optional)
**Requirements**: SESSION-01, SESSION-02, SESSION-03, SESSION-04, SESSION-05, SESSION-06
**Plans**: 4 plans
**Completed**: 2026-02-03

**Success Criteria:**
1. User can start a lesson and create a session with 1-hour TTL
2. User can complete stages within an active session
3. User cannot complete stages without an active session
4. User can end a lesson and trigger completion flow (XP, progress, streak)
5. User can resume a lesson after app crash (session recovery)
6. User cannot be in multiple lessons simultaneously (concurrent session detection)

Plans:
- [x] 09-01-PLAN.md — GameSession models and service (Lua script, TTL, force-close)
- [x] 09-02-PLAN.md — Session endpoints (start, end) with completion flow integration
- [x] 09-03-PLAN.md — [Gap closure] Session validation in /progress/complete
- [x] 09-04-PLAN.md — [Gap closure] GET /sessions/current for session recovery

**Details:**
- Lua script atomically force-closes existing session when creating new
- 1-hour TTL (3600s) for session auto-expiry
- Redis key pattern: memora:gamesession:{user_id}
- XP calculation function inlined in sessions.py to avoid circular imports
- 403 NO_ACTIVE_SESSION for end without active session
- 404 for absent session on recovery (resource not found)

### Phase 10: Leaderboards

**Goal**: Competitive XP rankings via Redis sorted sets (daily/weekly/all-time)
**Depends on**: Phase 5 (XP and streak mechanics), Phase 9 (session context for subject)
**Requirements**: LEADER-01, LEADER-02, LEADER-04
**Plans**: 3 plans
**Completed**: 2026-02-03

**Success Criteria:**
1. User can view all-time XP leaderboard with top N players
2. User can view daily XP leaderboard (resets at midnight Asia/Amman)
3. User can view weekly XP leaderboard (resets Friday midnight Asia/Amman)
4. User can retrieve their rank position with neighbors context
5. Leaderboards update atomically when XP is awarded

Plans:
- [x] 10-01-PLAN.md — Leaderboard service foundation (models, ZSET operations, composite scoring)
- [x] 10-02-PLAN.md — Leaderboard API endpoints (GET /leaderboard/{type}, GET /leaderboard/{type}/me)
- [x] 10-03-PLAN.md — XP award integration (session end updates leaderboards)

**Details:**
- Composite score formula: xp + (1.0 - (timestamp % 1e9) / 1e9) for tie-breaking
- Dense rank via ZCOUNT of scores strictly greater
- Unranked users get rank = total + 1, xp = 0
- ISO week format (%G-W%V) for weekly board keys
- Subject-specific boards updated when session provides subject_id

### Phase 11: Scheduled Tasks

**Goal**: Automated maintenance for streaks, sessions, and leaderboards
**Depends on**: Phase 5 (streaks), Phase 9 (sessions), Phase 10 (leaderboards)
**Requirements**: SCHED-01, SCHED-02, SCHED-03
**Plans**: 4 plans
**Completed**: 2026-02-03

**Success Criteria:**
1. Users who miss activity have streaks reset at midnight Asia/Amman
2. Expired session keys are removed hourly
3. Daily leaderboard archives yesterday's data and creates new key at midnight
4. All scheduled tasks are idempotent (safe on retry/duplicate execution)

Plans:
- [x] 11-01-PLAN.md — Task infrastructure foundation (DocType, Prometheus metrics, task_utils.py)
- [x] 11-02-PLAN.md — Core scheduled tasks (streak_reset, session_cleanup, leaderboard_reset)
- [x] 11-03-PLAN.md — Task Dashboard page with manual trigger API
- [x] 11-04-PLAN.md — Scheduler hooks registration in hooks.py

**Details:**
- Task Admin role created via after_install hook
- prometheus_client for task metrics (Grafana compatible)
- Delete streak_date on reset (clean state per wallet.py pattern)
- Session cleanup TTL -1 only (safety net, not primary expiry)
- Cron entries staggered (00:05, 00:10, 00:15) to avoid overlap

## Milestone Summary

**Key Decisions:**
- Fingerprint uses stable UA components (no versions) for device recognition
- Lua script for atomic operations (device registration, session force-close)
- Composite score for leaderboard tie-breaking (earlier achiever wins)
- SCAN (not KEYS) for all Redis iteration in scheduled tasks
- Idempotency via has_run_today() checks

**Issues Resolved:**
- Device limit race conditions (Lua script atomicity)
- Session TTL memory leaks (1-hour auto-expiry)
- Timezone-naive streak resets (AMMAN_TZ in all tasks)
- Non-idempotent task execution (has_run_today guards)

**Issues Deferred:**
- LEADER-03: Streak leaderboard (deferred to v1.2)
- LEADER-05: Daily leaderboard 30-day archival clarity (deferred to v1.2)
- Profile lookup for leaderboard display names (deferred to v1.2)

- avatar_url=None placeholder in leaderboard responses
- TODO: fetch subject name from Frappe in progress.py
