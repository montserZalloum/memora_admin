### Integration Details

**Phase-to-Phase Wiring:**
- Phase 29 → 30: Schema (autoname, check_password, mobile, PBKDF2) consumed by Frappe APIs
- Phase 30 → 31: Frappe APIs (5 functions) consumed by all 10 FastAPI endpoints
- Phase 31 → 32: JWT identity (PLAYER-#####) consistent across all event handlers and APIs
- Phase 29 → 32: user field (temporarily kept) removed in Phase 32

**Identity Model:**
- 0 residual `doc.user`, `profile.user`, `pp.user`, or `{"user": ...}` references
- All Redis keys use PLAYER-##### identity
- All SQL queries use `pp.name` or `name` field

**Redis Namespace:**
- All event handlers and scheduled tasks use `get_fastapi_redis()` (not `frappe.cache()`)
- Two-pronged invalidation pattern (direct + pubsub) applied consistently

## Critical Wiring Chains Verified

### Password Hash Chain
Phase 29 `_hash_password()` → Phase 30 `verify_player_password()` / `set_player_password()` → Phase 31 `/auth/player/login` / `/auth/player/password-reset/confirm`
- All use PBKDF2-SHA256 via `update_password()` / `check_password()` with `doctype="Memora Player Profile", fieldname="password"`

### JWT Identity Chain
Phase 29 autoname → Phase 30 API returns `player_id: profile.name` → Phase 31 `create_access_token(user_id=player_id)` → JWT `sub: PLAYER-#####`

### Session Invalidation Chain
Phase 30 `_invalidate_player_sessions()` → Phase 31 password reset confirm → Phase 32 plan_change_sync + device_sync → Redis DEL `memora:session:{PLAYER-#####}`
